# Research: ناوگان ورکر مقیاس‌پذیر چندسروره

**Date**: 2026-09-15 | **Spec**: [spec.md](spec.md) | **Plan**: [plan.md](plan.md)

همه موارد NEEDS CLARIFICATION در Technical Context با بررسی کد موجود + بهترین‌پراکتیس‌ها حل شد. هیچ مورد بازی برای فاز طراحی نماند.

---

## R1 — اجرای SSH از گیت‌وی (نصب خودکار)

- **Decision**: کتابخانه `asyncssh` (async-native) برای اتصال‌های نصب؛ اجرای هر نصب به‌صورت job پس‌زمینه (asyncio Task + جدول وضعیت در Postgres)، نه داخل ریکوئست.
- **Rationale**: گیت‌وی کاملاً async است (FastAPI + httpx + aioredis)؛ `paramiko`/`fabric` سینک‌اند و در event-loop بلوکه می‌کنند. `asyncssh` هم password و هم key را native پشتیبانی می‌کند و با `asyncio` همان حلقه گیت‌وی کار می‌کند.
- **Alternatives considered**: paramiko در threadpool (کار می‌کند ولی مدیریت timeout/concurrency سخت‌تر)؛ agentless مثل Ansible (وابستگی سنگین جدید برای چند دستور داکر/کامپوز).
- **Key gotcha**: اعتبارسنجی host-key در اولین اتصال — اثر انگشت در اولین نصب نمایش/ثبت و بعد پین می‌شود (نه `known_hosts=accept` کور). timeout هر مرحله جدا + لاگ خط‌به‌خط فارسی. نصب‌های هم‌زمان با سمافور (~۱۰ اتصال) + تایم‌اوت per-connection تا FD خفه نشود.

## R2 — نگهداری رمز/کلید SSH در مرکز

- **Decision**: رمزنگاری متقارن `Fernet` (پکیج `cryptography`)؛ کلید مستر فقط در env مرکز (`FLEET_MASTER_KEY`)؛ برای هر سرور کلید جدا مشتق‌شده با HKDF از (مستر + شناسه سرور)؛ ستون DB فقط ciphertext نگه می‌دارد.
- **Rationale**: Fernet استاندارد، بررسی‌شده و ساده است (AES-CBC + HMAC)؛ مشتق per-server یعنی لو رفتن یک ردیف، بقیه را لو نمی‌دهد؛ چرخش مستر = بازرمزنگاری همه ردیف‌ها با یک job یک‌باره، بدون نیاز به ورود مجدد رمزها.
- **Alternatives considered**: Ansible Vault / HashiCorp Vault (سرویس جدید، خلاف سادگی)؛ هش یک‌طرفه (برای رمز SSH غیرممکن است — باید برگشت‌پذیر باشد).
- **Key gotcha**: هیچ‌وقت plaintext در لاگ/اکسپشن/پاسخ API نماند — آبجکت اتصال فقط در حافظه رانر نصب زندگی می‌کند و بعد از اتمام صفر می‌شود؛ موقع حذف سرور، ردیف سکرت + ciphertext فوراً پاک می‌شود.

## R3 — کتابخانه نمودار داشبورد

- **Decision**: `recharts` برای نمودارها (خطی/میله‌ای/دایره‌ای) + SVG دستی برای «نقشه سلامت گره‌ها» + `Intl.NumberFormat('fa-IR')` برای اعداد فارسی.
- **Rationale**: استک فعلی React + Tailwind + framer-motion است و هیچ کتابخانه نموداری نصب نیست؛ recharts کامپوننتی و React-native است (سریع‌ترین entegration)، برای RTL با `direction: rtl` و محور معکوس جواب می‌دهد؛ نقشه سلامت گره‌ها نمودار آماده ندارد و با SVG سبک تمیزتر درمی‌آید.
- **Alternatives considered**: lightweight-charts (سریع‌تر ولی imperative/غیر-React و فارسی‌سازیش بیشتر کار دارد)؛ SVG کاملاً دستی (برای ۴ نمودار + تاریخچه، هزینه ساخت و نگهداری بالا).
- **Key gotcha**: polling هر ۵ ثانیه فقط داده خام را می‌آورد؛ `isAnimationActive={false}` روی سری‌های زنده + رینگ‌بافر کلاینت (۶۰–۱۲۰ نقطه آخر) + memoize آرایه‌ها (وگرنه هر tick کل چارت re-render و پرش دارد)؛ نسخه major پین شود (drift بین v2 و v3)؛ تاریخچه چندروزه از endpoint جدا (downsample شده) نه از همان endpoint زنده.

## R4 — حلقه مقیاس خودکار ورکرها

- **Decision**: سیگنال = عمق صف + بار در حال اجرا به‌ازای هر سرور (همان متریک dispatcher)؛ کنترلر هر ۶۰ ثانیه `desired_workers` را داخل [min, max] مدیر تنظیم می‌کند؛ ایجنت هر گره مثل امروز reconcile می‌کند.
- **Rationale**: از همان عددی استفاده می‌کند که dispatcher برای انتخاب ورکر استفاده می‌کند (تک‌منبع حقیقت)؛ سقف مدیر جلوی انفجار هزینه/منابع را می‌گیرد؛ بازه ۶۰ ثانیه از نوسان (flapping) جلوگیری می‌کند — مقیاس لحظه‌ای لازم نیست چون بک‌تست‌ها دقیقه‌ای‌اند.
- **Alternatives considered**: مقیاس بر اساس CPU (نیاز به متریک قابل‌اتکا از هر گره + کالیبراسیون)؛ مقیاس دستی خالص (خواسته کاربر صریحاً خودکار بود).
- **Key gotcha**: scale-down فقط ورکرِ بیکار را می‌کشد (drain اول)؛ hysteresis (آستانه بالا/پایین جدا) تا تعداد ورکر نوسان نکند؛ تغییر desired همیشه در پنل قابل‌مشاهده و override دستی همیشه بر خودکار اولویت دارد.

## R5 — ذخیره تاریخچه متریک

- **Decision**: دو لایه — Redis برای «زنده» (آخرین نمونه هر گره، TTL کوتاه) + Postgres (`fleet_metrics`) برای تاریخچه با rollup دقیقه‌ای؛ خام ۵ ثانیه‌ای فقط ۲۴ ساعت نگه داشته می‌شود.
- **Rationale**: برآورد حجم: ۱۷٬۲۸۰ نمونه/روز به‌ازای هر متریک هر گره با گام ۵ ثانیه؛ با ۶ متریک و rollup دقیقه‌ای برای تاریخچه چندروزه، چندصد هزار ردیف می‌شود — برای Postgres با ایندکس (server, ts) و purge روزانه کاملاً عادی است؛ Redis Timeseries ماژول اضافه می‌خواهد و لازم نیست.
- **Alternatives considered**: نگه‌داشتن همه خام ۵ ثانیه‌ای برای همیشه (رشد بیهوده جدول)؛ Prometheus (سرویس جدید برای داشبوردی که recharts + Postgres جواب می‌دهد).
- **Key gotcha**: job روزانه purge (همراه retention فایل ۳۰ روزه)؛ endpoint تاریخچه همیشه downsample برمی‌گرداند (حداکثر ~۵۰۰ نقطه) تا موبایل خفه نشود. برآورد حجم: ~۱۱۰ بایت/ردیف → ~۱۷هزار ردیف/روز/گره ≈ ‏۲ مگابایت/روز/گره (۱۰ گره × ۷ روز ≈ ۱۳۰ مگ)؛ هرگز one-row-per-metric (۵ برابر حجم)؛ خام ۵ ثانیه‌ای فقط ۲۴–۴۸ ساعت، بعد rollup دقیقه‌ای.

## R6 — انجین محلی روی گره (گره کامل)

- **Decision**: هر گره همان ایمیج/کامپوز انجین مرکزی را اجرا می‌کند (نسخه پین‌شده از مرکز)؛ کلید LLM مشترک از state کنترل‌پلن به env انجین همان گره تزریق می‌شود؛ ورکر همان گره `VIBE_ENGINE_URL=localhost:8899` می‌گیرد.
- **Rationale**: «گره کامل» یعنی محاسبه واقعاً پخش شود؛ پین نسخه از مرکز + آپدیت مرحله‌ای (US-11) جلوی واگرایی نسخه‌ها را می‌گیرد؛ ورکر→انجین روی همان ماشین یعنی تأخیر صفر و عدم وابستگی به شبکه برای محاسبه.
- **Alternatives considered**: انجین مشترک مرکزی (همان گلوگاه امروز — با تصمیم B کاربر رد شد)؛ بیلد جدا برای هر گره (واگرایی قطعی).
- **Key gotcha**: حداقل منابع گره کامل بالاتر است (تست توان US-07 دقیقاً برای همین است)؛ سلامت انجین هر گره جدا از سلامت ورکرهایش چک می‌شود (دو چراغ جدا در نقشه سلامت).

## R7 — مدل کوپن جدید vs موجود

- **Decision**: تکامل `coupons.py` فعلی (نه بازنویسی): سقف فری می‌شود «۱ بک‌تست روزانه + ۱ سوارم هفتگی» بدون انباشت؛ کوپن‌های welcome موجود به‌عنوان «اعتبار دائمی» (مثل رفرال) حفظ می‌شوند تا حق کاربران فعلی ضایع نشود؛ `grant_key` یکتا + تراکنش اتمیک برای claim؛ برگشت کوپن فقط برای خطای سمت ما.
- **Rationale**: جدول `coupons` و `grant_key` ضدنژاد همین امروز درست طراحی شده؛ تغییر فقط در سیاست grant/claim است؛ سازگاری عقب‌رو (welcomeها می‌مانند) جلوی اعتراض کاربران فعلی را می‌گیرد.
- **Alternatives considered**: جدول جدا برای اعتبار رفرال (دو منبع حقیقت برای «آیا کاربر حق اجرا دارد» — نه)؛ بازنویسی کامل (ریسک رگرسیون روی قانون ۲ جایزه رفرال که تازه فیکس شد).
- **Key gotcha**: ترتیب مصرف (اول روزانه، بعد اعتبار دائمی) باید در یک تراکنش اتمیک باشد وگرنه مسابقه دو تسک هم‌زمان دو بار مصرف می‌کند؛ رد اعتبارسنجی ورودی اصلاً به claim نمی‌رسد.
